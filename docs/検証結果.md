## 段階検証 2 の実装と実行結果（2026-10-06）

### 実装した動作

- LLM は `gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}/grok/v1/chat/completions`。Cloudflare token は `cf-aig-authorization`、保存 BYOK `default`、`cf-aig-no-wholesale: true`。provider Authorization を送らない。既定 model は `grok-4.6`、権限は AI Gateway Run。アプリに xAI キーを要求しない。
- `completePackageCopy` は JSON schema を要求し、schema 関連 4xx だけ一度外す。401 / 403 / 429 / 5xx は再試行しない。schema 再試行を含め timeout 60 秒。空本文・不正 JSON は失敗とし、エラーには token / provider の応答本文を載せない。
- カタログの保存済み Releases / Advisories を読む。初号は21日 lookback、以後 semver cursor と既出 GHSA Story で判断。未来・日付不明・pre-release・分類不能を除外。rank は security 100 / major 80 / minor 60、patch は human 20、古い major は human 10。
- 重要度→公開日時→パッケージ名で並べ、ユーザごと8パッケージまで。全ユーザの掲載集合を決めてからコピーを共有生成する。複数 GHSA は紙面1項・StoryはGHSAごと。空号・hold・silent・deferred に LLM を呼ばない。
- URL・数字・kind を検査し、失敗した項だけテンプレ。数字の検査は入力と導出日付の集合照合であり、意味全体の自動検証ではない。ライブでの品質確認は引き続き必要。
- 未適用の 0002 / 0003 を既存カタログへ追加。各 migration の SQL と適用履歴は同じ transaction。旧 0001 の履歴なし DB の移行もテスト。旧 drift DB とは混ぜない。
- コピー、night_decisions、Story、Investigation、Judgment、cursor、全ユーザの号を単一 transaction で確定。号保存が失敗すれば全部 rollback。同日再実行は保存号を返し、過去日付の新規生成は拒否。比較は別 DB。旧 held は新しい版で resolved に更新する。

### 接続と課金の仕様

「xAI に直接支払い、Cloudflare からそのキーで呼ぶ」は BYOK で対応できる。生成設計の REST 経路に必要な値は次のとおり。

| 項目 | REST Chat Completions の設定 |
| --- | --- |
| URL | `https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/v1/chat/completions` |
| Authorization | `Bearer {Cloudflare API token}`。対象 account の **Workers AI Read** が必要。xAI キーをここに入れない |
| Gateway | `cf-aig-gateway-id: chobitnews`。BYOK を保存した Gateway を明示する |
| model / 入力 / 出力 | `xai/grok-4.6` / `messages` / `choices[0].message.content` |
| Provider Keys | xAI の有効な API キーを alias **`default`** に保存。REST は他 alias を参照しない |
| 課金の固定 | **Require provider credentials = On**（`byok_only: true`）。適用できるキーが無ければ 400。Cloudflare Unified Billing に落とさない |

最小の接続検証では `messages: [{ role: "user", content: "Reply with OK." }]` を送り、本文と課金元を確認する。`cf-aig-no-wholesale: true` を付ければ、そのリクエストでも Unified Billing への fallback を禁止できる。Gateway の設定が On ならこのヘッダは追加の確認用になる。

保存 BYOK のみを指定し、provider 用 Authorization を送らず、Gateway の `byok_only: true` とリクエストの fallback 禁止を維持した呼び出しである。したがって保存キーの取り出し・xAI 認証・このモデルの呼び出しは成功したと判断できる。`default_config: false` を理由にキーを更新する必要も、この成功経路のために追加の token 権限を要求する理由もない。xAI の請求明細自体は未確認。

検証済みの接続設定は前掲 `/grok/v1/chat/completions` + `cf-aig-authorization` + `cf-aig-byok-alias: default` + `model: grok-4.6`。最初の REST の認証ヘッダー混同と `/openai` の provider 選択誤りは特定できたが、正しい REST 経路で報告された 2049 は未解決。native 比較では token の新規作成も入っているため、Cloudflare の REST と BYOK の対応に不具合があるとまでは断定しない。

アプリへの反映には `src/llm.ts` の接続先・認証・`input` → `messages`・`choices[0].message.content` の読み取りをまとめて変更する必要がある。今回は接続調査として成功設定と必要変更を記録し、コード移行やデプロイは実施していない。JSON schema 付きの朝刊生成、実データでの品質・timeout は今回の `OK` 接続検証の範囲外。

1. Cloudflare ダッシュボードの AI > AI Gateway で、curl が指す account / Gateway と同じものを開く。
2. Provider Keys に xAI の API キーが保存されているか確認する。xAI での課金やキー発行だけでは Cloudflare にキーは登録されない。Worker Secret への登録も Gateway の Provider Keys とは別。
3. Cloudflare REST 経路なら alias は `default`。provider-native 経路なら `cf-aig-byok-alias` で指定した alias、未指定なら `default` を確認する。
4. Provider Keys が存在しても API 登録の場合は Secrets Store の命名と provider configuration の provider_slug / alias の一致を確認する。キーの値を読む必要はない。
5. 提示された curl の model は REST 用の `xai/grok-4.6` で、生成設計・公式カタログと一致する。最初に提示された入力欄に model が無いことは、この curl の model 未指定を示さない。

修正後は同じ Gateway へ最小リクエストを送り、本文と BYOK の使用を確認する。**Require provider credentials を Off にして回避しない。** xAI 直接支払いの意図を保つため、保存キーの適用を直す。なお、前段のコード調査で見つかった形式の不一致は別の問題であり、この Gateway エラーの直接原因とは扱わない。

調査環境の readiness は secrets / runtime variables / outbound identities が空。ネットワーク設定にも `api.cloudflare.com` / `api.x.ai` は含まれない。これは **調査環境側**の不足であり、Cloudflare Worker の外向き接続制限を示すものではない。対象外ホストへの迂回接続は試していない。

| 目的 | 追加で必要なもの |
| --- | --- |
| Gateway 設定・ログを読む | `api.cloudflare.com` への通信許可、対象 Account ID、AI Gateway Read を持つ Cloudflare token（環境の secret として設定） |
| 設計の REST 推論を再現する | 対象 account の Workers AI Read token を `CLOUDFLARE_API_TOKEN` に、Account ID を `CLOUDFLARE_ACCOUNT_ID` に設定。xAI キーは Gateway 側 BYOK のままでよい |
| xAI 直接接続と比較する場合だけ | `api.x.ai` への通信許可と、対象チームの xAI API キーを環境の secret に設定。Gateway 調査だけなら直接キーの共有は不要 |

設定変更を行う段階では AI Gateway Edit、BYOK 登録では Secrets Store の作成・デプロイ権限も確認する。調査だけに Edit は必要ない。API キーの値はチャットやログに出さない。

次に必要な証拠は、失敗した実行場所（CLI / Worker / ダッシュボード）、送信先 URL、HTTP status、エラー本文、可能なら Gateway log ID / 発生時刻。401 / code 10000 なら Cloudflare の account・token・Workers AI Read を先に確認し、provider credentials 不足の 400 なら Gateway 選択と BYOK default を先に確認する。xAI 側の認証・残高・モデル制限はエラー本文と provider log で切り分ける。
